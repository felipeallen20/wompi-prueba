# CONVENTIONS.md

Global conventions for this project. All agents and contributors (human or AI)
must follow these rules at all times.

## 0. Canary Rule

Every response generated by an AI agent while working on this project **must
start with the literal word `Felipe:`**. This is a canary that confirms the agent
has read and is actively following this file. If a response does not start with
`Felipe:`, treat it as a signal that the agent has lost context — re-share this
file before continuing.

## 1. Language Rule

**Everything in this project is written in English.** No exceptions inside the
repository:

- Variable, function, class, and file names
- Database table and column names
- API endpoints, request/response payloads, DTOs
- Code comments and docstrings
- Documentation (README, this file, architecture docs, task lists, etc.)
- Commit messages, branch names, pull request titles and descriptions
- UI copy, labels, and any user-facing text
- Error messages and log messages

The **only** exception is direct conversation with Felipe (the developer) — that
communication can be in Spanish.

## 2. Code Quality Rules

### 2.1 No Magic Numbers
Never hardcode unexplained literals. Extract them into named constants with a
clear, descriptive name.

```ts
// Bad
const total = amount + 5000;

// Good
const BASE_FEE_COP = 5000;
const total = amount + BASE_FEE_COP;
```

### 2.2 Single Responsibility per File
Each file does exactly one thing. If a file mixes concerns (e.g. validation +
persistence + formatting), split it into separate files.

### 2.3 No Business Logic in Controllers
Controllers and routes are only responsible for: parsing the HTTP request,
delegating to a use case, and shaping the HTTP response. All business rules live
in the domain/application layer — never in the controller.

### 2.4 Small Functions
Functions do one thing and stay short enough to read without scrolling. If a
function needs a comment to explain what a block of it does, that block is
probably a function waiting to be extracted.

### 2.5 Self-Explanatory Code
Prefer descriptive names over comments. A comment should explain *why* something
is done, never *what* is being done — the code itself should make the *what*
obvious.

### 2.6 Strict Folder Boundaries
Respect the layers defined in `ARCHITECTURE.md`. Domain code never imports from
infrastructure. Infrastructure adapters never contain business rules. No
"reaching across" layers to save a few lines, ever.

### 2.7 Testing Mindset
Write tests alongside the code, not after the fact. Every use case and every
critical validation needs a unit test. Target: **more than 80% coverage** on both
frontend and backend, matching the test's evaluation rubric.

## 3. Git Rules

- One branch per feature: `feature/<short-description>`, `fix/<short-description>`.
- Commit messages in English, imperative mood, following Conventional Commits
  where possible:
  - `feat: add credit card validation use case`
  - `fix: correct stock decrement on failed payment`
  - `test: add unit tests for CreateTransactionUseCase`
- Small, focused commits — one logical change per commit.
- Open a Pull Request per feature before merging into `main`, even when working
  solo — it keeps the history clean and reviewable.
- Never commit secrets, API keys, or `.env` files.
- Never use the payment provider's company name anywhere in the public
  repository (name, README, code, comments, commit messages, branch names) —
  per the test's explicit instruction.
